# ADR-0011: アーカイブ保存時の行選別

- 日付: 2026-07-27
- 状態: proposed（`/cockpit-build M10` 起動＝プラン承認で accepted）
- 関連: spec §4.4 / §4.4.1 / §7、milestones/M10-archive-line-retention/（起案元プラン）
- 先行: ADR-0008（ミラー方式）、ADR-0009（per-root 進捗と resume 検証）。**いずれも本 ADR で改訂しない**

## 文脈

出力先 `H:\マイドライブ\dev\context` に蓄積された 31 セッション / 287MB / 67,235 行を実測した結果、
解析に使える情報は約 0.05%（人間発話 616 件・136KB）にすぎず、残りは機械的ノイズだった。
最大の要因は `attachment` の 209MB、うち `hook_success` ＋ `async_hook_response` で 203MB。
これは上流リポジトリの ECC フックが毎ツール呼び出しごとに claude 自身の JSONL へ書き込む
正常時 payload であり（stderr は全体で 0.7MB のみ＝失敗ログではない）、cockpit は spec §4.4 の
「ハーネス素材としての完全性を優先する」に従って逐語コピーしていた。

ユーザーは「ストックする情報の削減」「後で解析するための必要と思える情報だけがストックされるように」
と指示し、解析用の派生ファイルを併置する案（ファイルを増やす方向）は明確に却下した。

したがって決めるべきは、**逐語完全コピーという spec §4.4 の方針を選別保存へ改めるとき、
どの層で・どの粒度で選別し、既存の append-only 不変条件とミラーの resume 機構をどう保つか**である。

## 決定

- **D-1（選別の位置＝スプール書き込み時）**: 選別は `src/main/archive/archiver.ts` が
  スプールへ追記する時点で行う。ソース JSONL（claude 管理下）は従来どおり読み取り専用。
  ミラー（`archive/mirror/**`）は「スプールのバイト複製」という現行の位置づけを変えないため、
  ADR-0008 のミラー方式、ADR-0009 のバイト前方一致による resume 検証は**無改訂で成立する**。
  スプールが選別済みになるだけで、ミラー層から見た世界は変わらない。
  代替案「ミラー書き込み時に選別する」は、スプールと出力先のバイト前方一致を壊し
  ADR-0009 の検証機構を行単位へ再設計する必要があり、影響範囲が不相応に大きいため採らない。

- **D-2（粒度＝行単位・逐語保持）**: 保持する行は**元の行テキストをそのまま**追記する。
  再シリアライズ（`JSON.parse` → `JSON.stringify`）はキー順・エスケープ・未知フィールドの
  表現を変え、spec §7 の寛容パーサ原則（未知フィールドを保全して将来のバージョン追従に備える）を
  内側から崩すため行わない。
  帰結として、1 行の中の一部ブロックだけを落とすこと（`image,text` 行から画像だけを除く等）は
  できない。実測でこれは実害にならない:
  - 最大の無駄である `tool_result` は **必ず単独行**（3,691 行 / 30.5MB、`text` との混在 0 件）。
    行ごと破棄しても人間の発話を 1 件も失わない
  - `image,text` は 36 行 / 4.88MB のみ。人間のキャプションが同一行にあるため**行ごと保持**する。
    4.88MB は選別後の総量に対して許容範囲であり、画像だけを落とす価値は再シリアライズの代償に見合わない

- **D-3a（`queued_command` は保持する）**: エージェント実行中に人間が割り込んで打った発話は
  `attachment.type: "queued_command"` の行にしか存在せず、`type: "user"` 行として再出力されない。
  H: 実測で 45 行中 26 行が `origin.kind: "human"`、うち `type:"user"` 行に同一本文があるのは 2 行のみ
  （約 24 件がこの行だけの記録）。内容は「ながい。３行が原則だ」「お前のくそ長い前置きのせいで
  前提が見えない」等、軌道修正の瞬間という解析価値が最も高い発話だった。
  `origin` の値による条件分岐は行わず**全量保持**する（D-3 の「保持に倒す」を貫き、
  CLI 側の `origin` 表現の変化に依存しない）。45 行 ≒ 30KB で容量影響は無視できる。
  起案時にこれを破棄側へ置いていたのは誤りで、usability レビューの指摘を受けて訂正した。

- **D-3（判定は denylist）**: 保持すべき行を列挙する allowlist ではなく、破棄する行を列挙する
  denylist とする。未知の `type` / `attachment.type` / `system.subtype`、および JSON として
  不正な行は**保持**に倒す。spec §7 の寛容パーサ原則と同じ倒し方であり、claude CLI の
  アップデートで追加された行種を無言で失わない。
  代償は追従コスト（新しいノイズ行種は denylist に載るまで保持され容量が膨らむ）であり、
  「取りこぼさない」ことと引き換えに受容する。

- **D-4（再開オフセットの永続化と検証）**: 現行の `archiver.ts` は再アタッチ時の読み取りオフセットを
  **アーカイブファイルのサイズ**から復元している（`offset = fs.statSync(archivePath).size`）。
  これは「アーカイブのバイト列 ＝ ソースの先頭からのバイト列」という等式に依存しており、
  選別によって崩れる。
  サイドカー `archive-state.json`（`{ sourceOffset, lastUuid }`、temp+rename で書き込み）を
  セッションのアーカイブディレクトリに置き、再アタッチ時は錨（下記）との一致を確認してから
  `sourceOffset` を採用する。

  実装で確定した分岐集合（`ResumeDecision`。`attach()` の `switch` が網羅性をコンパイラに強制する）:
  `sidecar`（一致 → `sourceOffset` 採用）/ `scan`（不一致・サイドカー不在・不正 → 錨 uuid をソース側で
  走査して復元）/ `zero`（アーカイブが真に空）/ `unsafe`（矛盾状態 → **後述**）。

  - **錨は「アーカイブ末尾行の `uuid`」ではなく「`uuid` を持つ最後の行」**（末尾の uuid 無し行は
    後方に読み飛ばす）。`lastUuid` 側も同じ意味論（保持行を後方走査した最後の非 null uuid、
    無ければ前値を維持）に揃える。両者の非対称は実際に重複追記を招いた
  - 追記とサイドカー更新は原子的に束ねられない。**追記を先に行い**、サイドカー更新前の
    クラッシュは「不一致 → 走査で復元」の経路で吸収する。取りこぼし（記録の欠落）より
    重複追記のリスクを取り、その重複を uuid 検証で潰す設計とする
  - **サイドカー不在は legacy（M10 以前の逐語アーカイブ）を含め無条件 `scan`**。アーカイブの
    バイトサイズをオフセットに使う経路は設けない。「サイドカーが無いなら逐語アーカイブのはず」は
    偽の推論で（選別済みアーカイブでもサイドカーは失われうる）、行途中からの読み直しにより
    破棄行の断片混入と重複追記を実際に引き起こした。逐語アーカイブでも `scan` は同一の
    オフセット（錨行直後 ＝ アーカイブサイズ）に着地するため機能低下はない（実データ 10 セッションで確認）
  - **どの分岐が算出したオフセットでも、採用前に「行境界（0 または `\n` の直後）に着地しているか」を
    構造的に検証する**（`isSourceOffsetAtLineBoundary`）。行中オフセットからの読み出しを禁止する
    回帰トリップワイヤ
  - サイドカーの `sourceOffset` は**確定オフセット**であり、読み込み途中の部分行のバイトを含まない
    （揮発の読み取りカーソルと分離する）。含めると再開時に行の前半が永久に失われ、後半が
    不正 JSON として R-5 に拾われてアーカイブに混入する
  - **`uuid` を持たない保持行は実在する**（訂正）。起案時に「保持対象の全行種は `uuid` を 100% 保有し、
    `uuid` を持たない行は全て破棄対象」と書いたが、`~/.claude/projects` の 581 ファイル実測で
    **保持されるが `uuid` を持たない行が 1,349 行**見つかった（`agent-name` 1,332 / `frame-link` 10 /
    `custom-title` 7。いずれも denylist 未収載なので D-3 により保持される）。
    帰結として、`scan` 経路で復帰したとき錨より後ろにある `uuid` 無し保持行が 1 回だけ重複追記されうる
    （実測で「最後の保持行が uuid 無し」だったのは 581 中 1 ファイル ≒ 0.17%）。重複は次回以降
    サイドカーが錨と一致するため収束し、取りこぼし・既存内容の破壊・append-only 違反は伴わない。
    この残余は許容し、解消は followups とする
  - サイドカーは `fsSink` のミラー対象外（`transcript.jsonl` と `metadata.json` のみを扱う）なので
    出力先を汚さない
  - **DB 列にしない理由**: サイドカーをアーカイブディレクトリに同居させると、SQLite が失われても
    アーカイブ単体で再開状態を自己記述できる。「DB は復旧可能な派生状態、スプールが正」という
    ADR-0008 以来の位置づけを崩さない

- **D-4a（`unsafe` = 一次記録の watch 停止）**: 再開状態が矛盾していて安全な復帰点を決められない場合
  （アーカイブが空なのにサイドカーが uuid を主張する、非空かつ錨が皆無でサイドカーも一致しない、
  算出オフセットが行境界に着地しない）は、**そのセッションのアーカイブ記録を開始せず** `onError` で
  可視化する。自動再試行は行わない。
  ADR-0009 の safe-stop は**派生物（ミラー）**の停止だったが、こちらは**一次記録**の停止であり非対称である。
  spec §4.4 は「記録の完全性はここ（スプール）で担保し」と述べており、この判断はそれとのトレードオフを
  明示的に選ぶものである: **壊れた記録（重複・断片混入。append-only なので事後修復不能）よりも、
  可視の停止を選ぶ**。停止したセッションのアーカイブは無変更で残り、ユーザーは新しいセッション
  （新 session_id）で記録を再開できる。アプリ内からの復帰操作は設けない（followups）。

- **D-5（既存データは移行しない）**: 既存の保存済みアーカイブ・ミラー済みデータには一切触れない
  （ユーザー明示指示「既存のコンテキストを修正する必要はない」）。1 ファイル内で
  「前半＝選別前・後半＝選別後」の混在を許容し、境界マーカーも埋めない
  （append-only のアーカイブに cockpit 由来のメタ行を差し込むと、claude の JSONL 形式に
  異物が混じり寛容パーサの前提が汚れる）。

## 帰結

- spec §4.4 の「ハーネス素材としての完全性を優先する」は**選別保存**へ改める（出荷時に更新）。
  「元ファイルは一切変更しない」「削除・編集機能は設けない（append-only）」は不変のまま
- **同じ H: コーパスに出荷ポリシーを適用した実測で 303.0MB → 29.8MB（保持率 9.85%、約 90% 削減）**。
  人間発話・アシスタント応答・thinking・ツール呼び出し・ルール発火の証跡は全量残る。
  起案時の見積り「約 11MB / 3.8%」は誤りだった（保持行ごとの envelope バイトをブロック単位の
  集計から落としていた）。残余の主因は assistant 行 21.4MB（thinking 6.9MB ＋ envelope）と
  `image,text` 4.88MB
- `tool_result`（Bash stdout・Read したファイル本文）が失われる。「エージェントが何を見て判断したか」の
  生データは残らず、`tool_use` の引数（何を実行しようとしたか）と `thinking`（なぜそうしたか）が残る。
  M9（目的完了時の評価）の LLM 入力はユーザー発言全量優先なので影響は小さいと見込むが、
  M9 の実装が M10 より後になる場合は入力設計に本 ADR を参照した注記を置く
- denylist の追従が必要になる。claude CLI が新しいノイズ行種を追加した場合、denylist に載るまでは
  保持され容量が膨らむ（無言の欠落より容量増を選ぶ、という D-3 の意図どおりの挙動）
- 選別前後が混在するアーカイブが残る。解析側は「古いセッションにはノイズが含まれる」前提で
  集計する必要がある
- 上流（ECC フック側）が JSONL へ書く量そのものは減らない。cockpit のアーカイブが小さくなるだけで、
  claude 管理下の元 JSONL は従来どおりの大きさである（本アプリの関知外）
