# ADR-0013: 新規セッション開始時の git 同期（デフォルトブランチ移動と pull）

- 日付: 2026-07-28
- 状態: accepted（2026-07-28、`/cockpit-build M11` 実装・出荷）
- 関連: spec §2 / §4.1 / §4.2 / §4.6、milestones/M11-git-sync-on-launch/（起案元プラン）
- 先行: TD-7（目的ライフサイクルと再起動復帰。`--continue` は起動時 cwd 前提）、TD-5（Windows での claude spawn）

## 文脈

ユーザー要件:

> 新規セッションを開始した時、選択されているフォルダがgitリポジトリと紐づいていれば、
> 当リポジトリのデフォルトブランチに移動して最新をpullさせるようにする。
> ただし、未commitのファイルが残っていれば、commitを促すアラートダイアログを表示させ、ブランチは移動しない

cockpit の責務は spec §2 で「起動・表示・記録」に限定されている。git 操作はそのいずれでもない
**作業環境の準備**であり、責務を1つ増やす判断になる。加えて git 操作は cockpit の他の副作用
（アーカイブ・DB・pty）と違い、**ユーザーの作業ツリーという app 外部の資産を書き換える**。
したがって決めるべきは、この副作用を「どの起動経路に・どこまで踏み込んで・失敗時にどう振る舞って」
入れるか、そして spec §4.1（CLI の対話 UX を一切損なわない）と両立させる境界である。

## 決定

- **D-1（対象は「新規セッション」起動のみ）**: git 同期を試みるのは `paneLaunchStart`
  （＝「＋ 新規セッション」ダイアログ確定）経路だけとする。
  - 「再開」（TD-7、`--continue`）は**対象外**。`--continue` は前回会話の続きを復元する操作であり、
    その前提であるブランチを勝手に動かすのは復元の意味を壊す。要件の文言も「新規セッションを開始した時」。
  - ペイン内の `/clear` `/resume` による claude 側セッション切替も**対象外**。アプリは pty を素通しする
    だけでこれらを検知して介入する経路を持たず、持たせることは spec §4.1 に反する。

- **D-2（git 同期は起動の前提条件ではない）**: git がどう転んでも claude は必ず起動する。
  未コミットでブロックされた場合も、pull が失敗した場合も、git が無い場合も、セッションは通常どおり
  開始する。要件が禁じているのは「ブランチの移動」であって「セッションの開始」ではない。
  cockpit の中核責務（記録）を、付随機能の失敗で止めない。

- **D-3（層の分割）**: 判定は純関数、実行は副作用モジュール、束ねはコーディネータに置く。
  - `src/shared/gitSync.ts`（純関数・test-first）: `git status --porcelain` 出力のパース、
    デフォルトブランチの解決、`{ 現在ブランチ, 作業ツリー状態, デフォルトブランチ }` から
    「ブロック／移動＋pull／pull のみ／スキップ」を決める `planRepoSync`、および表示文言の生成。
    fs・child_process・Electron を参照しない。
  - `src/main/git/gitCli.ts`（副作用の集約）: `child_process.execFile` で git を叩く唯一の場所。
    Result 型を返し throw で握り潰さない。
  - `src/main/git/repoSync.ts`: 上2つを束ね、アラート表示は注入された port 経由で呼ぶ
    （Electron `dialog` への依存を持ち込まないので unit テスト可能）。
  - 呼び出しは `PurposeCoordinator.startNewSession`。同クラスは既に「新規セッションダイアログが
    確定したとき何が起きるかを決める唯一の場所」であり、順序（git 準備 → spawn）の所有者として適切。
    IPC ハンドラ層に順序ロジックを置かない（handlers.ts は検証と dispatch に限る、という既存の位置づけを守る）。

- **D-4（未コミット判定は untracked を含む）**: `git status --porcelain=v1 -z --untracked-files=normal`
  のエントリが1つでもあれば「未コミットあり」とする。ignore 済みファイルは含めない。
  要件の「未commitのファイル」の文字どおりの読みであり、「commit を促す」という目的
  （新規追加ファイルこそ commit 漏れしやすい）にも合う。
  代替案「tracked の変更のみをブロック対象とする」（untracked は checkout/pull を妨げないので通す）は、
  ダイアログの発火頻度は下がるが、ユーザーの明示要件から離れるため採らない。
  **2026-07-28、起案時の未決論点としてユーザーに諮り、本案（untracked を含める）で確定した**
  （`/cockpit-build M11` 起動時の確認）。なお `planRepoSync` の入力は
  `{ hasTrackedChanges, hasUntracked }` に分けたまま保ち、判定を純関数1箇所に閉じる。

- **D-5（デフォルトブランチの解決はローカル情報のみ）**: 解決順は
  `refs/remotes/<remote>/HEAD` の指す先 → ローカル `main` → ローカル `master`。
  remote は `origin` を優先し、`origin` が無く remote が1つだけならそれを使う。
  `git remote show <remote>`（ネットワーク往復）は**行わない** — 起動を待たせる時間が読めないため。
  いずれでも解決できなければ「スキップ（理由を可視化）」とし、推測で checkout しない。

- **D-6（pull は `--ff-only`）**: ローカルにプッシュ済みでないコミットがあるときに、勝手にマージコミットを
  作らない。非 fast-forward は失敗として可視化する。`--rebase` も採らない（履歴を書き換える操作を
  無断で行わない）。`git fetch` + `git merge --ff-only` 相当を `git pull --ff-only` 1コマンドで行う。
  **改定（review iter1, M4）**: remote はあるが対象ブランチに upstream が設定されていないリポジトリでは
  `pull --ff-only` は毎回 "no tracking information" で失敗し続ける。これは `checkout`/`pull` の実行結果
  に関する actionable な失敗（非 fast-forward・認証エラー等）とは性質が異なる（構成の欠落であり、リトライ
  で解決しない）ため、`checkout` 後に upstream の有無を確認し、無ければ `pull` を試みない。`failed` は
  あくまで実行した git コマンドが実際に失敗した場合に限る。
  **訂正（review iter2, M1）**: この「pull を試みない」結果を当初 `skipped` として返していたが、
  `checkout` 自体は既に実行され、ブランチは実際に動いている（`switch-only`/`checkout-and-pull` 経由の
  場合）。それを `skipped`（＝何も起きていない）と表示するのは、起きた事実（ブランチ移動）と矛盾する
  自己矛盾だった。`synced{ switched, pulled: false, pullSkippedReason }` として返し、ブランチが動いた
  事実と pull を見送った理由の両方を正確に伝える。`skipped` は「ブランチ状態について何も分からない／
  何も変わらない」場合（デフォルトブランチ未解決、既にデフォルトブランチかつ remote 未設定）にのみ残す。

- **D-7（他ペインが使用中のリポジトリは移動しない。modal はブランチ移動が必要な場合のみ）**: 起動しよう
  としているペインの cwd が属するリポジトリのルートが、**claude が実行中の別ペインの cwd が属する
  リポジトリのルートと一致する**場合、`checkout` と `pull` を**無条件に**行わない。`pull --ff-only` も
  稼働中エージェントの作業ツリーの tracked ファイルを書き換え HEAD を進める操作であり、
  稼働中のエージェントの足元でそれが起きるのは、spec §4.1 が守ろうとしている「CLI の対話 UX を損なわ
  ない」の最も直接的な違反にあたる（`checkout` だけを特別視しない）。比較はリポジトリルートの正規化パス
  で行う（Windows のためケース非依存・区切り正規化）。
  ただし D-9 のアラート（`dialog.showMessageBox`）を出すのは、**ブランチの移動（`checkout`）が実際に
  必要だった場合に限る**: 既にデフォルトブランチかつクリーンで、実行すれば `pull` のみだったはずの
  ケースでは、ブロックした事実そのものはペイン内の通知行のみで伝え、対話を遮る modal は出さない
  （同一リポジトリを複数ペインで使う構成での modal 頻発を避ける usability 上の配慮。「同期を行わない」
  という決定自体は両ケースで一貫している。区別するのは通知の強さだけ）。
  加えて、同一リポジトリへ**ほぼ同時に**複数ペインから新規セッションが開始された場合（どちらの claude も
  まだ起動していないため、稼働中ペインの検知だけでは検出できない）に `checkout`/`pull` が競合しないよう、
  リポジトリルート単位の in-flight ロック（`main/git/repoSyncLock.ts`）で直列化し、ロック保持中の
  リポジトリへの後続の起動も同じ `blocked-busy`（この場合は常に modal で知らせる — 先行する起動自身の
  分岐先がまだ確定していないため、ブランチ移動の要否を安価に判定できない）として扱う。
  `RepoSyncOutcome.blocked-busy` はどちらの経路で block されたかを `cause: 'running' | 'launching'` で
  区別し、通知文言も分ける（「claude が実行中」／「別ペインの git 同期が実行中」）— 前者は claude が
  既に動いている事実、後者はまだ動いていない事実であり、同じ文言で伝えるのは不正確。
  - **却下した代替案（review iter1 → iter2 で再考・却下）**: 「既にデフォルトブランチかつクリーンなら
    busy でも `pull` を実行する」という緩和を一度採用したが、`pull --ff-only` 自体が稼働中エージェントの
    作業ツリーを書き換える操作である以上、D-7 が防ごうとしている事象そのものであり、ユーザー承認済みの
    要件（plan.md R-6「ブランチ移動も pull も行わずアラートで知らせる」）を無断で緩めるものだった。
    「同期を一切行わない」という決定は維持し、modal を出すか通知行のみにするかだけを usability 上の
    理由で使い分ける（上記）ことで、要件を緩めずに modal 頻発の問題を解決する。

- **D-8（非対話・タイムアウト必須）**: git が認証プロンプトを出してブロックすると、ユーザーから見て
  「新規セッションボタンが固まった」状態になる。実行時は `GIT_TERMINAL_PROMPT=0`、
  `GCM_INTERACTIVE=never`、`GIT_ASKPASS`/`SSH_ASKPASS` を無効化した環境を渡し、
  さらにコマンドごとにタイムアウト（照会系 5 秒 / checkout 20 秒 / pull 30 秒）を課す。
  タイムアウトは失敗として可視化し、起動は続行する（D-2）。

- **D-9（アラートはネイティブ modal、それ以外はペイン内の通知行）**: 要件が名指しした
  「commit を促すアラートダイアログ」と D-7 のブロックは `dialog.showMessageBox`
  （`paneSettingsConfirmActivePurposeCwdChange` の既存の前例に倣う）。
  それ以外の結果（移動＋pull 成功、スキップ、pull 失敗）は modal を出さず、ペインヘッダ下の
  通知行に出す。成功のたびに modal を出すのは起動フローの妨げであり、失敗を握り潰すのは
  silent failure 禁止に反する — その中間として「必ず見えるが操作を止めない」表示を採る。
  **改定（review iter1, M8）**: 通知行は既定で1行に切り詰め、`title` ツールチップと「詳細」トグルで
  全文（blocked-dirty の変更ファイル一覧等）を展開できるようにし、「×」で明示的に閉じられるようにする。
  当初案は全文を常時表示しており、複数行の内容（変更ファイル一覧）が `flex:1` のターミナル領域の高さを
  恒久的に奪い、xterm.js の再フロー（fit + pty.resize）を誘発していた。既定表示を1行に保つことで、
  「必ず見えるが操作を止めない」という本来の意図を、ターミナル自体を圧迫しない形で達成する。

- **D-10（設定によるオン/オフを設けない）**: 要件は無条件の挙動として書かれている。トグルは
  `app_settings` とその UI を増やす割に、この機能が破壊的でない（D-2/D-4/D-6/D-7 でガード済み）ため
  見合わない。必要になったら別マイルストーンで追加する。

## 帰結

- cockpit の責務に「起動前の作業環境の準備」が1つ加わる。spec §2 の「含む」に明記して、
  責務の輪郭を曖昧にしないこと（M11 出荷時の spec 更新に含める）。
- 作業ツリーへの副作用は `checkout` と `pull --ff-only` の2つだけ。`stash` `reset` `clean` `merge`
  `rebase` `commit` は**行わない**。破壊的操作を無断で行う経路を作らない。
- git がインストールされていない環境でも cockpit は従来どおり動く（D-2）。
- append-only 不変条件・元 JSONL 非改変・pty 素通しには一切影響しない（git 実行は spawn 前に完結する）。
